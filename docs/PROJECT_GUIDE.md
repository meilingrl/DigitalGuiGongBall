# 如何理解和介绍这个项目（更新于 2026-10-21）

原项目是一套课程高保真前端原型：内容、模板和多个业务模块已经可演示，但登录为跳转，投稿只在组件内存中，雕刻工具未驱动几何，三维模板共用 GLB。2026-10-16 阶段先完成可验证的全栈创作闭环；2026-10-21 进一步让文化阅读、三维观察、创作和作品回看连起来。原文件、课程范围和历史验证记录继续保留。

## 这次产品整合做了什么

新版采用同一套米白、墨绿、衬线字体与间距。首页让游客先观察球体，再选择三个文化主题；每篇文章旁边就是可操作的三维结构，读完也可以带着已调整的参数进入工坊。登录后返回原意图；作品保存后有自己的详情、真实 PNG 和来源回链，首页读本人最近作品。

过去的文化展馆原文、课程计划和模拟业务保留为页脚存档。新导览重用课程配图并标注其性质，具体事实链接到博物馆原始资料。没有把模拟积分、用户量、展览预约或商城包装成真实后台。

## 值得面试讨论的问题

**为什么继续 Vue，选择 SQLite？** 保留现有内容和技术积累，把时间用于业务闭环。SQLite 无需云账号和独立数据库服务，事务和文件持久化足以支撑本地单进程演示。它不是多实例服务的扩展设计：未来需评估异步数据库访问、备份保留/加密和迁移运维，再决定是否切换数据库。

**登录页为什么不能代表权限实现？** 路由守卫只改善体验；真正权限在每次服务端作品查询和更新中用 `owner_id` 过滤。不能相信客户端提交的用户 ID。会话随机令牌放在 HttpOnly Cookie，数据库只保留摘要；退出删除服务端会话。相关代码在 `server/auth.ts`、`server/app.ts`，相关真实 HTTP 失败场景在 `server/tests/api.test.ts`。

**两个页面编辑同一件作品会怎样？** 每次更新带版本号，SQL 原子执行 `WHERE id=? AND owner_id=? AND version=?`，成功后版本递增。旧页面得到 409，前端保留草稿并提供读新版本入口；这是乐观并发控制，不是自动合并。请求晚于页面退出或显式重新读取完成时，也必须用编辑周期标识忽略过期响应，避免错误跳转或覆盖新页面状态。

**版本号和幂等键为什么缺一不可？** 版本号保护两个不同编辑意图不互相覆盖；请求键用来确认同一次操作。保存实际提交后响应丢失，直接带旧版本重试会409，而重新POST会重复创建。现在业务变化与 `(owner_id,key)` 的原响应记录同事务提交，相同请求可在重启后重放。前端持久保存不可变key/载荷，同时把后续编辑留作下一次意图。401仅代表本次确认被认证拦截，不能据此清掉此前未知提交。另一标签登录其他账号也不能让旧意图随Cookie漂移：请求携带预期账号，服务端只做一致性比较，真正归属仍取会话与ownerSQL。`tests/reliable-save.integration.test.ts` 用真实HTTP提交后丢弃响应，再重启、重登和恢复验证，而非永远成功的Mock。

**为什么备份SQLite不能直接复制主文件？** WAL模式下已提交数据可能仍在辅助日志中。维护命令通过SQLite一致性快照生成新文件，再校验完整性、外键和已知结构；恢复从不覆盖当前文件，并撤销旧会话。独立审查还发现SQL删空白导致结构签名碰撞、发布时外来WAL改变恢复结果，已用失败回归推动token/实际结构检查与发布前后文件身份检查。其边界是可信本地目录，不是生产灾备或恶意操作系统竞态防护。

**镂空究竟是不透明模型还是贴图？** `src/three/ornament.ts` 构造有厚度的球面纹样框与连接结构。射线测试确认开孔中心可穿过，边框实际挡住射线；密度、模板和开孔尺度改变顶点。各层拥有独立几何与材质，展开与剖视帮助理解层次。限制是风格化数学生成，不是文物扫描复原；裁切截面也没有实体封盖。

**构建通过后，为什么还需要浏览器和进程测试？** 类型检查不会发现 GPU 不可用、材质过曝或移动布局遮挡。数据库重开测试也不同于真实进程退出。`scripts/verify-restart.mjs` 从空库启动编译后服务，通过 HTTP 写入、正常重启、更新、强制终止和重登再读；它验证已提交数据在进程终止后的恢复，不证明断电、磁盘损坏或生产灾备。截图和浏览器路线补充了另一层证据。

**怎样把旧页面真正融入新产品？** 页面之间需要可追踪的业务关系。`shared/inspirations.ts` 为三篇导览提供稳定 ID；`src/data/studies.ts` 将文章、模板和观察步骤关联，当前配置经共享 Schema 校验后进入登录返回地址。保存时来源成为作品元数据，详情可以反向回到文章；首页近期作品直接查询本人数据库。这个边界比把多个旧页面放进导航更容易解释和验证。暂未实现阅读进度、内容管理系统或行为分析。

**为什么作品保存和图片上传分开？** 配置是继续创作的依据，图片是看清作品的辅助材料。`useAtelierDocument` 只在真实保存响应后推进版本，`useWorkPreview` 捕获该响应中的配置，再执行版本检查 PUT；图片失败有自己的重试提示。`AtelierStage.exportPreview` 复用已有 WebGL 渲染器、用独立对象和相机离屏渲染，结束后恢复场景状态。几何重建有延迟，截图仍需使用被确认的那份配置；后端再次验证 owner、版本、PNG 尺寸、CRC 和解压大小。

**浏览器验证发现了哪些单元测试看不到的问题？** 实际离屏图的纯色背景曾经过额外的色调映射，与舞台颜色不同；修复后用透明图层合成，真实 PNG 浅色左上为 `#eeeae0`、深色四角为 `#141c1a`。WebKit 还会复用同 URL 的已解码旧图：即使数据库更新、节点重建和 `no-store` 都成立，用户仍可能看到旧图。现在同版本重生成会使用新的 UUID 请求地址，作品版本继续保护配置一致性。真实浏览器深浅图片更新、HTTP 参数边界和 GPU 状态恢复测试各自验证不同部分，不能互相替代。

**兼容性为什么影响一个新增来源字段？** 旧客户端可能带着尚未确认的请求回来。如果给缺失的来源字段自动填 `null`，被校验后的载荷摘要会改变，原幂等键可能被误判为另一请求。新增字段在请求与草稿里保持可选，旧请求原样重放；响应缺字段按空来源呈现。`tests/editor-lifecycle.test.ts` 与 `server/tests/preview.test.ts` 验证这一边界。
